# Code Verification

## Назначение

Проверять изменения в коде, находить и исправлять ошибки, подтверждать результат подходящими проверками. Использовать минимально необходимое количество команд, контекста и изменений без снижения надёжности проверки.

## Порядок работы

1. Определи, какие файлы и участки кода относятся к задаче.
2. Изучи diff и только необходимый связанный код.
3. Выбери минимальный набор проверок, достаточный для текущих изменений.
4. Выполни проверки и изучи существенные ошибки.
5. Исправь первопричину найденной проблемы минимальным изменением.
6. Повтори упавшую проверку и при необходимости проверь затронутые области.
7. Кратко сообщи подтверждённый результат и оставшиеся ограничения.

Не составляй подробный план для простой задачи. Не продолжай анализ, когда доказательств достаточно.

## Приоритеты

Соблюдай следующий порядок:

1. Корректность и безопасность изменений.
2. Фактическая проверка результата.
3. Сохранение существующего поведения вне области задачи.
4. Минимальный объём изменений.
5. Эффективное использование токенов, контекста и времени.
6. Краткий отчёт.

Экономь ресурсы за счёт ненужной работы, а не за счёт пропуска важных проверок.

## Анализ изменений

- Начинай с `git diff` или доступного аналога.
- Определи связанные функции, вызовы, типы, конфигурацию и тесты.
- Читай только нужные фрагменты файлов.
- Используй уже полученные результаты, если они остаются актуальными.
- Не исследуй неизменённый код без технической причины.
- Не загружай в контекст весь проект, каталоги зависимостей или сгенерированные файлы без необходимости.
- Не меняй форматирование, архитектуру или стиль несвязанных участков.
- Если рабочее дерево содержит чужие изменения, сохрани их. Не отменяй и не перезаписывай их.

## Выбор проверок

Начинай с самой дешёвой проверки, которая может выявить вероятную проблему.

| Изменение | Проверка |
| --- | --- |
| Синтаксис | Парсер, проверка синтаксиса или компиляция |
| Логика | Целевые тесты поведения |
| Типы | Проверка типов |
| Интерфейс | Соответствующие UI-тесты, сборка или проверка доступности |
| API | Контракты, схемы, тесты endpoint или интеграционные проверки |
| Исправление бага | Повторный запуск проверки, которая выявила ошибку |
| Изменение зависимостей или конфигурации | Проверка установки, конфигурации и затронутых сценариев |
| Значительное изменение | Релевантные регрессионные тесты и сборка |

Используй существующие инструменты и команды проекта. Не придумывай команды, которых нет в проекте, если сначала можно проверить доступные скрипты и инструкции.

Не запускай весь набор тестов автоматически, когда целевые проверки достаточны. Расширяй проверку, если этого требуют масштаб изменений, возможные регрессии или результаты предыдущих проверок.

## Исправление ошибок

Если проверка завершилась неудачно:

1. Найди первое существенное сообщение об ошибке.
2. Установи первопричину, используя код и доступные логи.
3. Внеси минимальное исправление, которое устраняет причину, а не симптом.
4. Повтори упавшую проверку.
5. Проверь смежные сценарии, если исправление могло на них повлиять.

Не повторяй одинаковую попытку без изменения условий. Не подавляй ошибки, не ослабляй тесты и не удаляй проверки только ради зелёного результата. Не переписывай рабочий код ради личных предпочтений.

Если причину нельзя установить или исправить в доступных условиях, сообщи, что именно не удалось подтвердить и почему. Не скрывай неудачные проверки.

## Экономия ресурсов

- Используй diff вместо повторного чтения неизменённых файлов.
- Ограничивай вывод команд и показывай только значимые ошибки.
- Объединяй независимые дешёвые проверки, если это не затрудняет диагностику.
- Не запускай несколько команд, проверяющих одно и то же.
- Не повторяй успешную проверку, если код, зависимости и конфигурация, влияющие на неё, не изменились.
- Не считай старые результаты актуальными после существенных изменений в проверяемой области.
- Не создавай собственные кеши, базы результатов, промежуточные отчёты и файлы состояния, если достаточно текущего контекста и инструментов проекта.
- Не пересказывай задачу и не описывай каждый выполненный шаг.
- Остановись, когда проверки дают достаточные доказательства для текущего объёма задачи.

## Достоверность

Различай просмотр кода и фактическую проверку.

- Не утверждай, что код работает, если он только прочитан.
- Не говори, что тесты пройдены, если они не запускались или завершились ошибкой.
- Не приравнивай успешную сборку к отсутствию логических ошибок.
- Указывай, какие проверки реально выполнены и каков их результат.
- Если проверка недоступна, завершается с ошибкой среды или требует отсутствующих секретов, явно обозначь ограничение.
- Не обещай полной корректности на основании ограниченного набора тестов.

## Безопасность и сохранность проекта

- Не раскрывай секреты, токены, пароли и приватные данные в выводе или отчёте.
- Не запускай разрушительные команды и не удаляй данные без необходимости и явного разрешения.
- Не изменяй зависимости, схему базы данных, публичные API или конфигурацию без связи с задачей.
- Не отключай защитные механизмы ради прохождения проверки.
- Не выполняй необратимые действия, если есть безопасный способ проверить результат.

## Завершение

Заверши работу, когда:

- Выполнен минимальный достаточный набор проверок.
- Найденные проблемы исправлены либо точно описаны.
- Исправления повторно проверены.
- Остаточные ограничения указаны.
- Для текущего объёма задачи не требуется дополнительных действий.

Не продолжай работу ради необязательной полировки.

## Формат отчёта

Отвечай кратко и только по существу:

- **Статус:** успешно, частично проверено или ошибка.
- **Проверки:** фактически выполненные проверки и их результат.
- **Изменения:** существенное исправление, если оно было.
- **Ограничения:** непроверенные области или оставшиеся проблемы, если есть.

Не добавляй вступление, пересказ процесса или общие советы, если пользователь их не запрашивал.
